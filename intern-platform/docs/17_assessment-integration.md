# 17. 適性検査との統合設計（確定版）— 12ドキュメント読了後

作成日: 2026-08-20 / 入力: piecetimes-crm `docs/適性検査/`（企画要件定義 v1.0・実装仕様書 v1.0・ゲーミフィケーション企画書 v1.0・別紙A/A2/B/C/D/E/F/G/H）

---

> **補足（2026-08-20 ユーザー指摘）**: 適性検査は完成しきっていない可能性がある。実際、ドキュメント自身が未完成部分を明示している——①パイロット検証（n=200〜300）は未実施（別紙Dは「検証前」版） ②30特性換算行列はv0初期値（実測較正前） ③16タイプの出現分布は未確認・重み未較正 ④設問の一般学生版は存在しない ⑤本体側の実装状況は不明。**本統合設計はこれらを前提に組んである**: 共有パッケージは行列・重み・設問をすべて差し替え可能な設定として持ち（バージョン管理）、インターン側の審査エントリー回答が実質的な初回パイロットになる（分析スクリプトを同梱し、n蓄積後にα係数・因子構造・タイプ分布を確認して較正）。n≥200の検証完了までは「検証済み」表記を出さない（別紙D §8の表記規律に従う）。つまり**適性検査の完成を待つ必要はなく、インターン側が最初の実装者・検証者になる**。

## 1. 読了サマリー — 適性検査は「完成度の高い共有エンジン」

受領した適性検査は、ツナカレ本体（体育会）向けに設計された以下の一式で、**権利・心理測定・アルゴリズムの3面で実装可能な完成度**にある:

| 資産 | 内容 | インターン事業での価値 |
|---|---|---|
| 測定モデル | IPIP参考の自社起草ビッグファイブ（Lv.1=35問5分+追加15問）+ 妥当性チェック6種 + キャリア志向性10問（N1〜N10） | そのまま流用可（文脈のみ調整・§3） |
| 30特性ブリッジ | 企業の言葉（5要素×6特性）とBig5を換算行列でつなぐ。自社言い換え文言・行列v0まで完成（別紙G） | 企業側「求める特性」入力＝**インターン求人の構造化フォーマットに直結** |
| マッチング | 2チャネルP-E fit（職務要求適合×欲求供給適合）・調和平均・バンドスコア・Kelley縮約・プール内パーセンタイル。文献根拠付き（実装仕様書6章） | **マッチ提示エンジンとしてそのまま実装対象**。志向性10問がチャネルB、30特性がチャネルA |
| 16タイプ・カード | 8アーキタイプ×烈静。文言はBarnum監査済み（別紙A/A2）、シェアカード設計（別紙E）、相性コンビ・他己診断（別紙H） | 学生集客のバイラル装置として流用（一般学生版の文言調整のみ） |
| AI就活実利 | AI自己PR・ガクチカ骨子生成（ゲーミフィケーション企画書 14.1「3本の橋」①） | **14_acquisition の「ガクチカ言語化ツール」と同一物** → 実装を1回に統合 |
| 企業支援 | 攻略ガイド・オファー文面AI（別紙F） | インターン企業への**AI推薦文・面談前ガイド**として流用 |

## 2. 重大発見 — 15の「グリーンフィールド」結論を訂正

別紙B/F/H には「既存認証」「NotificationService」「community_recruitments」「GCS画像基盤」「camelCaseレスポンスの既存API規約」「featureブランチ→PR」等、**稼働中のツナカレ本体コードベースの存在を前提とした記述**が多数ある。CRMと同様、**本体コードは `tkoba-piecetimes` アカウント側に実在する可能性が高い**（tsunakereoff側の tsunakare-backend/frontend/management-frontend はそのミラー用の空受け皿と推定）。

**含意**:
- 共通IDは「Supabaseで新規に作る初代」ではなく、**ツナカレ本体の既存認証・学生IDとの整合設計**が必要（確認するまで確定できない）
- 適性検査（G1・秋リリース予定）はツナカレ本体側で実装が進む可能性が高く、**同じエンジンを二重実装すると将来必ず割れる**
- → 本体コードの確認が実装開始前の必須条件（§6の依頼1）

## 3. 統合アーキテクチャ（確定方針）

### 3-1. 共有パッケージ方式 — エンジンは1つ、プロダクトは2つ

```
@tsunakare/assessment（純粋TypeScriptパッケージ・DB/フレームワーク非依存）
├─ item-bank/        設問データ（バージョン・パック・因子・逆転・文脈バリアント）
├─ scoring/          逆転処理→因子平均→Kelley縮約→パーセンタイル（ノルム注入式）
├─ traits/           30特性換算行列（別紙G v0）＋バンドスコア
├─ typing/           16タイプ判定（別紙A 1.3）＋僅差デュアル
├─ matching/         2チャネル適合度（調和平均・非対称バンド・精度重み）
└─ validity/         妥当性チェック判定（V1〜V6合議制）
        ↑ 参照                     ↑ 参照
ツナカレ本体（体育会G1）        ツナカレインターン（本事業）
体育会ノルム・部活文脈設問       一般学生ノルム・一般文脈設問
```

- **すべて純粋関数**（入力: 回答・ノルム・企業プロファイル → 出力: スコア・タイプ・適合度）として実装し、テストファーストで固める（16 §6 の方針どおり。課金と並ぶ最重要テスト対象）
- どちらのプロダクトからも同じ計算結果が出ることが、将来の共通ID統合時のデータ互換を保証する

### 3-2. 文脈バリアント — 同一因子構造・二つの文言

別紙Dは約6割が部活文脈（FoR効果狙い）。一般学生には合わないため:
- `v1-athletic`（別紙Dそのまま・ツナカレ本体用）と `v1-general`（同一因子・同一構造で部活文脈→学業/サークル/バイト/チーム活動に置換）の**2バリアントを同一バージョン系列**で管理
- 例: C2「決めた練習メニューは、最後までやり切る」→ 一般版「自分で決めた学習や作業の計画は、最後までやり切る」
- 一般版の起草はこちらで実施 → ユーザーレビュー → **パイロット検証は別々に実施**（体育会ノルムと一般学生ノルムは別物として蓄積。マッチングはプール内パーセンタイル方式のため設計変更不要）

### 3-3. インターン事業のファネルへの組み込み（14のオファー階段を精緻化）

```
[公開] ティザー診断（5〜8問・30秒）→「あなたは◯◯タイプの気配」＋LINE登録導線
   ※正式スコアにはしない（Credé 2012: 極端な短縮は妥当性を損なう）。「気配」表現に留める
        ↓
[審査エントリー] Lv.1フル35問＋志向性10問＋妥当性チェック（≒10分）
   → 正式なBig5・30特性・タイプ・志向性が確定＝審査F5の入力・実績書の初期データ
   ※「応募直前の必須化で回答率が最大化する」という本体側の決定（企画要件 6.7-6）と同型の設計
        ↓
[メンバー] タイプカード（シェア=獲得ループ）／AI自己PR・ガクチカ言語化（就活実利）
   マッチ提示 = チャネルA（求人の求める特性 max8・重み付き）×チャネルB（N1〜N10 と求人の提供環境）
        ↓
[企業側] 求人構造化フォーマットに2項目追加【要件確定】:
   ①「求める特性」30特性から最大8個+重み（チャネルA） ②「提供できる環境」N1〜N10対応10項目（チャネルB）
   AI推薦文・面談前の攻略ガイド（別紙Fの流用）で面談確約の質を担保
```

- 審査5軸との整理: F5（志向明確度）の入力に志向性10問+非同期ヒアリングを使用。**適性検査スコア自体は合否に使わない**（実装仕様書の「足切りに使わない」原則をインターン審査でも堅持。合否はF2実績・F3課題・F4行動のまま）
- 16タイプ文言は体育会モチーフだが普遍性が高い（司令塔・参謀等）。一般版は「プレー」「練習」等の語を「活動」「チーム」に調整した軽微改稿で対応（A2のBarnum監査規律を維持）
- 相性コンビ・他己診断（別紙H）は**インターン版G1には含めない**（サークル・友人グループでの拡散装置としてPhase 2候補。まず審査・マッチングのコアを固める）

### 3-4. データモデルの整合（16 §3 を実装仕様書に合わせて改訂)

実装仕様書のスキーマ（assessment_versions / items / packs / responses / personality_profiles / company_trait_profiles / matching_scores / trait_mapping_matrices）を**正とし**、16 §3 の assessments / assessment_results をこの形に置き換える。インターン固有の memberships / achievements / matches / placements / 契約スナップショットは16のまま。将来ツナカレ本体と共通ID化する際、personality_profiles が同一スキーマなら移行はID紐付けだけで済む。

## 4. コンフリクト回避（本体G1と並行開発になる場合）

1. **エンジンは共有パッケージ、データは別プール**: コードの二重実装を避けつつ、ノルム・回答データは互いに独立（検査バージョンとノルムIDで分離）
2. 本体側の実装状況を確認するまで、**共有パッケージはインターン側リポジトリ内のパッケージとして先行実装**し、本体側が使える形（純粋関数・依存ゼロ）を保つ
3. 別紙B（スポンサークエスト）・別紙F（本体側UI）はインターン事業のスコープ外。触らない

## 5. 実装計画への反映（16 §7 の改訂）

- W1: 基盤+**@tsunakare/assessment のスコアリング/タイプ判定/マッチングをテストファーストで実装**（設問データ投入含む・最重要成果物に昇格）
- W2-3: 公開サイト+ティザー診断+ガクチカ言語化（=AI自己PR基盤）
- W4-5: 審査エントリー（Lv.1フル+志向性+妥当性チェック+AI一次評価+adminキュー）
- W6: 企業（構造化フォーマット+求める特性/提供環境+契約同意）
- W7: マッチ提示（2チャネル適合度+AI推薦文+攻略ガイド簡易版）+11/2運用リハーサル
- W8: 総合テスト・リリース判定
- 追加成果物: `v1-general` 設問文言の起草（W1でドラフト→ユーザーレビュー）
