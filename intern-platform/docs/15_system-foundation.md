|---|---|---|
| tsunakare-backend | **空**（2026-07-28作成のプレースホルダ） | 器のみ |
| tsunakare-frontend | **空**（同上） | 器のみ |
| tsunakare-app | **空**（同上） | 器のみ |
| tsunakare-management-frontend | （同時作成・未確認だが同様と推定） | 器のみ |
| tsunakare-clubs | **ラクロスマニア**（JLAデータ→静的サイト生成のメディア。tsunakare.jp/clubs/ への設置を予定） | メディア資産 |
| rugbymania | ラグビーマニア（本事業資料もここ） | メディア資産 |
| piecetimes-crm | 非公開CRM（未確認・営業管理系と推定） | 業務ツール |
| eiyo-kanri / umamitensei-web | 別事業 | 対象外 |

**含意**: 共通IDについて「ツナカレ既存システムに合わせる」必要はない。**合わせる先がまだ無い**。つまりツナカレインターンで作る学生ID・プロフィール基盤が、そのまま**PieceTimes共通基盤の初代**になる。これは制約ではなく好機で、レガシー統合コストゼロで理想形から設計できる。

適性検査のセッションはアカウント上に確認できた（アーカイブ済み・ローカル実行のセッションのため、**このセッションからは中身を読めない**）。コードはGitHub上のどのリポジトリにも見当たらないため、統合には共有が必要（§4）。

## 2. 共通基盤のアーキテクチャ（提案）

### リポジトリ配置

空の器が既にあるので活用する:

| リポジトリ | 役割 |
|---|---|
| **tsunakare-backend** | 共通基盤: DBスキーマ（Supabase migrations）+ 共有API。学生ID・プロフィール・適性検査結果・企業アカウントはここが正 |
| **tsunakare-frontend** | 学生向けWeb（ツナカレインターンの公開サイト+メンバーページ。将来ツナカレ本体の学生向け機能も同居） |
| tsunakare-management-frontend | 運営管理画面（審査・掲載審査・請求・KPI） |
| rugbymania / tsunakare-clubs | メディア（既存のまま。学生向けWebへの導線を張る） |

※Phase 0 の実装速度優先で「まず tsunakare-frontend に Next.js + Supabase で一体実装 → Phase 1 で backend にスキーマ/APIを分離」でもよい。どちらでも共通IDの設計は同じ。

### コアスキーマ（共通ID基盤の初代）

```
students            … 共通ID（Supabase Auth: LINE/メールログイン）
student_profiles    … 氏名・大学・学年・所属（部活/団体/無所属）・志向サマリー
assessments         … 検査マスタ（type: 'aptitude_full' | 'aptitude_short' | 'screening_task' など, version）
assessment_results  … student_id × assessment_id, scores(jsonb), taken_at  ← 適性検査もここに載る
memberships         … プール会員資格（審査結果・行動信頼スコア・資格停止フラグ・招待枠）
achievements        … 実績書（審査課題・実務経験・企業評価の蓄積）
companies / jobs    … 企業・求人（構造化フォーマット）
matches / placements… マッチ提示・面談・稼働・転換（課金イベントの正）
club_units          … ツナカレ既存の部活単位データ（個人IDができた時点で students に紐付け）
```

- 学生は1つのIDでインターン期→新卒期を通す（13 §3の「一生モノのキャリアプロフィール」の実体）
- 適性検査・入口診断・審査課題を **assessments の型違い**として同一テーブル系に載せるのが統合の核。検査が増えても構造が変わらない

## 3. 適性検査との統合設計（診断系を「合わせる」の具体化）

### 設計原則: 入口診断・審査・適性検査を「同一アイテムバンクの深さ違い」にする

```
30秒志向診断（入口・集客フック）＝ 適性検査のショート版（5〜8問）
    ↓ 結果画面「フル版でより正確に」→ 会員登録
フル適性検査（メンバー特典・15〜30分）＝ 別セッションで開発中の本体
    ↓ スコアが審査F5（志向明確度）とマッチングの特徴量に流れる
審査課題（15分・職種別）＝ F3。適性検査とは別軸（能力実技）として並立
```

| 統合ポイント | 内容 |
|---|---|
| スコアの流用先① 審査 | 適性検査の結果を5軸フィルター（12 §2）のF5の入力にする。合否には弱く、マッチングには強く使う |
| スコアの流用先② マッチング | 求人の「採用目的タグ・求める志向」と適性スコアの適合度をマッチ提示の根拠に使い、推薦文にも反映（「◯◯適性が上位△%」） |
| スコアの流用先③ 企業表示 | プロフィールに適性タグとして表示（スカウトDB統合後は検索条件にもなる） |
| 集客との接続 | 入口30秒診断はフル検査と同じスコア軸の短縮版として設計（別物を2つ作らない）。診断→フル検査→審査が一本の階段になる（14 §3-2のオファー階段と一致） |
| データ | すべて assessment_results に共通IDで蓄積。検査のバージョン管理（version列）で設問改訂に耐える |

### 適性検査側との「契約」（これが決まれば両者は独立に開発できる）

適性検査セッション側から共有してほしいもの:
1. **スコア軸の定義**: 何次元・各軸の名前とスケール（例: 成長志向/安定志向/対人/構造化… 各0-100）
2. **設問数と所要時間**（ショート版を切り出せる構造か）
3. **実装形態**: Web（何のフレームワークか）/ 採点ロジックの置き場所（クライアント/サーバ）
4. **結果データの形**: JSONスキーマ

こちらから提供するもの: 共通ID（Supabase Auth）・assessment_results の書き込み口（APIまたは直接スキーマ）・結果表示ページの枠。

## 4. 依頼事項（ユーザーへ）

1. **適性検査のコード/仕様をリポジトリに push して共有してください**（例: `tsunakereoff/aptitude-test`）。このセッションに追加すれば直接読んで統合設計を確定できます。コードが未整理なら、§3の「契約」4点（スコア軸・設問数・実装形態・データ形式)のメモだけでも十分です
2. リポジトリ配置（§2: backend=共通基盤 / frontend=学生向けWeb）の承認、または「Phase 0 は一体実装」の選択
3. piecetimes-crm（非公開CRM）は未確認。企業アウトリーチの顧客管理をこのCRMに載せるかどうか、中身を確認してよいか
